## Product, attribution and fraud

Each signed-in account can generate one server-issued permanent code. Enforce unique owner and code in PostgreSQL. Suspension freezes new attribution or reward issuance according to the corresponding admin control. Existing awards and legitimate pending claims remain auditable. Use the canonical app origin to build links.

Use a first valid click from a server-issued, expiring first-party claim token. Development starting window is 30 days. Capture countable visits separately from signup starts, and use a random first-party identifier for estimated unique browsers. Ignore prefetch and obvious automated traffic and rate-limit collection. Refreshes and multiple links retain the first eligible assignment. Record the claim during account creation, independently of redirects. Direct Supabase signup without a verified server claim remains unattributed. Existing accounts cannot claim retrospectively.

Track pending verification, incomplete profile, review, qualified and rejected states. Qualification uses verified email, valid attribution, explicit review of a persisted profile, a meaningful professional identity and a relevant work, education or skills section. Reuse existing profile fields and permit missing optional details, partial dates and zero Gulf experience. Save and retry paths must converge on one reward per referred identity. Keep a bounded, keyed duplicate signal after deletion where justified by the retention policy. Keep repeated email/document signals, disposable domains, burst patterns and shared networks as review signals. Never reject solely for a shared IP, device or similar resume.

## Wallet and service authorization

The wallet adds flexible integer credits while preserving the narrower value of old service-specific grants and plans. Evaluate eligible pre-existing allowances for their service before spending flexible credits. Do not convert outstanding legacy entitlements into a different entitlement. New users start with zero wallet credits. Development defaults are +3 per qualified referral and costs of 3 for CV, 1 for Cover Letter, 2 for Q&A, and 3 for Mock Interview. Referral credits are non-expiring. Validate and audit changes. Snapshot cost at reservation and award value at issuance.

Use an append-only event ledger tied to source lots and reservation allocations. Use a transaction-level per-user lock, unique operation identities, and state-checked transitions for holds, settlement, release, refunds, expiry and reversal. Spend eligible lots in earliest-expiry order, followed by issue time and stable ID. A retry resolves against the original request and its artifact, while intentional new generation uses a new operation identity. Preserve source accounting when refunding. A reversal may recover only remaining or subsequently recoverable value under a documented policy and cannot make available credits negative.

Apply the credit gate on the server alongside the existing AI guard. Reserve only after input and ownership validation. Settle wallet and persistence in the same database transaction or via a durable result marker that reconciles atomically. Do not use the AI guard's best-effort finish callback as proof of a credit-backed saved result. Release failed calls. A stale hold may be released only after establishing that the result cannot still be published. All optimizer difficulty levels use the same initial service price. Regenerations are individually charged on success. Charge once for a new mock session. Existing sessions, answers, recorded batches and reports continue under their existing authorization and budget guards. Saved artifacts and exports have no wallet charge. Keep basic ATS and free profile features under existing controls.

Admins can select any user and grant complimentary access to selected premium services. Reuse the service-specific allowance mechanism with a specified number of uses and a required reason, record the grant in the admin audit trail, and let a successful eligible run use that allowance before wallet credits. Service pauses and AI limits still apply. Keep exposure estimates based on current service price and observed AI cost data. Reuse existing model, pause and budget controls. Keep pricing display and checkout availability separate.

## Future payments

Keep provider-specific financial records outside the wallet. The wallet's grant contract takes source, reference, owner, units and optional expiry. Source plus external business reference is idempotent. Future financial contracts include versioned products, plan, price and currency, order, attempts, invoices, subscription state and periods, refunds, chargebacks, immutable webhook receipts and reconciliation. Quota subscriptions can continue independently alongside wallet credits.

Commercial activation requires founder selection and provider account onboarding, pricing/tax decisions, branch-only sandbox credentials, server-created checkout, signature checks against raw webhook events, idempotent grants from verified state, reconciliation of delayed and out-of-order events, subscription lifecycle and refund tests, and explicit approval of live activation. A configuration switch alone cannot enable an unavailable checkout adapter. No real provider calls at launch.

## Launch configuration and rollback

Development migration defaults leave referral attribution and wallet enforcement disabled. After isolated deployment, an admin should enable both and verify the effective settings. Review the 30-day first-click window, +3 reward, premium costs 3/1/2/3, browser tracking cap of 60/hour, ten daily awards before manual review, non-expiring referral credits and hidden indicative pricing. Confirm that email confirmation is required. Honor existing approved service allowances, daily AI limits and service pause switches.

For Vercel, set the test Supabase URL and publishable/anon key and the matching server-only key on Preview for `feature/referral-credit-monetization`. Set the branch app URL and the corresponding test Auth redirect allowlist. Review and neutralize inherited database or payment configuration before deploying. The branch's Git-triggered deployment is deliberately disabled while this scope is being verified. A known test-only Vercel configuration is required before manual Preview or removing that branch guard. Use only synthetic accounts and route-level model fixtures for tests that need no real model, then sample genuinely live AI only within approved budget.

For approved production rollout, verify backup or accepted recovery and capture current config, exact main/deployment SHA and the pre-change Auth function/trigger inventory. Apply the numbered additive SQL in order. Deploy the verified code. Confirm a zero-credit user is gated and a complimentary user remains subject to existing limits. Verify real account confirmation, one award and one saved generation in an authorized rollout test account. If rollback is needed, pause affected services and referral issuance before reverting the app to the known-good deployment. Keep ledger, lots and attribution for reconciliation. Release only known stale reservations under the reconciler; restore prior Auth triggers only from the recorded recovery plan if necessary.

## Remaining limitations to verify before release

The assisted fraud policy can detect repeated qualifying emails, known disposable domains and excessive rewards per referrer. It avoids permanent rejection based on shared devices or networks. It does not validate identity, employment or resume authenticity. Existing database counters govern AI abuse. Paid subscriptions, payments, merchant onboarding, live webhook handling and real financial reconciliation remain future activation work. The browser and release evidence in the verification report determines readiness.
