# Persistent publishing — proposal only, not implemented

The current approved implementation has code defaults, live previews and browser-local drafts. Publish and restore are disabled. No database or API changes are included.

## Approval requested for a later implementation

Reuse existing Supabase; no new service. Add a numbered migration with an append-only `design_theme_versions` table (UUID primary key, validated JSONB settings, creator UUID, timestamp) and a singleton `design_theme_state` table (id constrained to 1, draft JSONB, published version UUID, previous version UUID, updated timestamp). Foreign keys retain known versions. Public clients receive no write permissions. Existing administrator authorization is rechecked on every server action. Server-side validation uses the allowlisted theme schema; arbitrary CSS is rejected.

Operations: save draft validates and stores draft only; publish validates and atomically creates a version and switches the published/previous pointer; restore atomically swaps pointers to validated versions. Use an optimistic expected-version argument to reject conflicting admin writes. A transaction/RPC performs version insertion and pointer update together, with locked-down execute permissions. Include bounded version retention after references are preserved.

Runtime: server reads only published settings through a dedicated narrow reader, falls back to the known-good code preset on missing/invalid storage, and serializes CSS variables into the website-only boundary before first paint. Cache the published record with a dedicated tag; invalidate after successful publish/restore. Do not cache private drafts in public output. Never put secret settings in the theme response. Resume rendering/PDF paths never read this configuration.

Required verification before enabling: unauthorized read/write attempts, invalid/injected configuration, concurrent publish conflict, transaction failure, rollback, fallback, cache freshness across sessions, first paint, all connected components and full resume preview/PDF regression. Migration must be tested in disposable DB before production execution. Founder approval of exact migration/actions is still required; this document alone is not authorization.

## 11 November recovery review — smaller option for founder approval
The two-table proposal above is not implemented. Source review found existing `site_content` (migration046), existing admin service-role writes and tag invalidation (`lib/admin/siteContent.ts`). For the smallest publish/one-step rollback scope, a narrower alternative is recommended:

- **Schema:** no new table or migration. Reserve one unpublished `site_content` row `design_theme_state`; store bounded JSON `{revision,current,previous}` in body. Keep browser drafts as they are; no server draft/history feature. Verify migration046 actually exists in target database before proceeding. A typed configuration table remains preferable if full immutable history is later required.
- **Security:** dedicated server-only read/write helpers, existing `requireAdmin` on every action; strict complete-schema validation, payload size limit and no arbitrary CSS. Keep row `published=false` so existing public RLS does not expose it. Public website receives only sanitized current settings via narrow server reader. Exclude this reserved row from general content editor/list/save paths so legal-copy editing cannot corrupt configuration. No service key in browser. Existing auth behavior unchanged.
- **Atomic publish/rollback:** store current and previous together in a single row update guarded by expected revision and updated_at; zero affected rows means conflict, never unconditional upsert overwrite. First creation must use insert and reject duplicate. Rollback swaps the two validated snapshots in one compare-and-swap update. No cross-row transaction/RPC needed for this bounded one-step model. Editor reload/retry on conflicts.
- **Caching/first paint:** dedicated design-theme tag with existing Next cache pattern, invalidate after successful action; affected route cache must also be revalidated and checked across two independent browsers. Serialize validated published variables on website boundary before hydration; avoid client reset to DEFAULT_THEME by passing identical initial settings. Code defaults on missing/invalid configuration; report admin read failures. Do not cache drafts publicly. Document renderers never read theme storage.
- **Tradeoff:** one-step rollback only, no append-only audit history. JSON-in-content is less explicit than a typed table but avoids a migration/new service. Multi-version audit/retention needs the earlier proposal instead.
- **Approval gate:** founder must choose this bounded option or versioned tables before persistence implementation. Test unauthorized writes, malformed payloads, conflicts, fallback, first paint, cache invalidation and rollback in a disposable environment before any release. No database/environment/auth/API changes were made during recovery.
